# Hermes's cron vs what Chelus needs

The conclusion of a read of Hermes Agent's scheduler (NousResearch/hermes-agent @ 99fcd69, MIT): `cron/` (44 modules, about 20,900 lines) and the cron tool in `tools/cronjob_*.py`. The parts that matter for Chelus are about 15,000 of those lines, listed under Reading status. This file is the port list for scheduling and proactive messages, the 1.0 blocker in [STATUS.md](../STATUS.md).

## What Hermes cron is

A job is a stored prompt (or script, or both) plus a schedule. A ticker inside the gateway process wakes every minute, finds jobs that are due, and runs each one as a fresh agent session with no chat history. The agent's final answer is posted to a chat. That posting is the whole of "proactive messages": Hermes has no separate push system, only jobs whose output gets delivered.

Schedules come in five forms: a bare duration (`30m`, recurring), `in 30m` (once), `every 2h`, natural phrases (`every monday 9am`, `weekdays at 9am`) compiled to cron, five-field cron with day and month names, and an ISO timestamp (once; a naive one is local time). One-shots default to one run and recurring jobs to forever; `repeat` caps either.

The model manages jobs through one tool with actions create, list, update, pause, resume, remove and run. The tool description tells it the prompt must be self-contained, the run cannot ask questions, and it should update an existing job rather than make a near-duplicate.

## The design rules

As with the brain, the rules matter more than any one file.

- **At most once, never twice.** The tick moves `next_run_at` forward *before* running the job, in the same save that records which slot it is firing. A crash mid-run loses that run; it never repeats it. Finite jobs bump their completed count before running, too. A ledger of runs (`executions`) records the instant each run was for, and only a `completed` row counts as proof a slot ran.
- **Missed runs collapse to one.** After downtime, a recurring job fires once to catch up, not once per missed slot. A slot is "late" past 300 s. Past the grace window (half the period, clamped to 120 s to 2 h) the backlog collapses into a single `catch_up` run, or is skipped with a logged reason if the job opted out. A one-shot more than 120 s past due is retired with a note, never fired late.
- **Pause and resume keep their place.** A slot that came due while paused fires on the next tick after resume.
- **Never silently finish.** A recurring job whose next run can't be computed goes to `state=error`, never to `completed`. One malformed job record never stops the scan of the others.
- **Fresh session, self-contained prompt.** No chat history, memory skipped, and the cron tool itself is switched off inside a cron run so a job can't spawn jobs. The prompt gets a fixed preamble (`_CRON_HINT`): your final answer is delivered automatically, so don't call send_message; answer `[SILENT]` to send nothing; put `[CRON_FAILURE]` alone on the first line to report failure; and never create new jobs because the prompt mentions a future time.
- **Silence is an answer, failure always speaks.** `[SILENT]`, `SILENT` or `NO_REPLY` as the whole reply, or its first or last line, suppresses delivery. Failures are always delivered, as one plain line saying what happened and what to do next.
- **Delivery is proven, not assumed.** A send counts only with a returned message id. A failed delivery is its own status (`delivery_failed`) and does not count as a job failure.
- **Idle time, not wall time.** The watchdog kills a run after 600 s with no activity, and time the device spent asleep doesn't count.
- **Retry only when nothing happened.** If the model was unreachable and zero API calls succeeded, a recurring job is re-run after 5, 15, then 30 minutes, and the interim failure notice is held back. Anything that reached the model is not retried.
- **Escalate once.** Three failures in a row add a nudge to the notice. Failures are grouped into incidents by error signature, alerted once and reminded after 6 h.
- **Scan what will run.** The user's prompt gets a strict injection scan at create, update and run time (8 patterns, `cronjob_prompt_scan.py`, plus invisible Unicode). The assembled prompt with skill bodies gets only the 4 directive patterns, because skills legitimately describe commands. A separate guard rejects jobs that would restart the gateway from inside it, which would loop forever.

## Constraints that are Chelus's own

- **Standard library only.** Hermes uses croniter. Chelus needs its own five-field matcher: lists, ranges, steps, names, and the classic rule that day-of-month and day-of-week are ORed when both are set. Stepping minute by minute with day and hour skips is plenty fast for a one-user phone.
- **No zoneinfo data on the phone.** Checked 2026-10-28: Python's `zoneinfo` has zero zones in Termux (no tzdata package), but `time.localtime` and `time.mktime` follow Android's timezone through libc and handle DST. So schedules use phone-local time through `time.mktime(..., tm_isdst=-1)`, and IANA zone names are not accepted unless tzdata gets installed. For a DST gap or overlap, take the earliest instant strictly after the base, as Hermes does with `fold`.
- **One process, one turn at a time.** Chelus has no gateway, worker pool or delivery queue: the Telegram bridge is the process. The tick goes in `Bridge.housekeeping`, the poll wait is capped to the time until the next due job, and a cron run blocks the bridge the way a chat turn does. Telegram holds incoming messages meanwhile, and the bridge already says it answers one turn at a time.
- **Doze and reboots.** Android will sleep the phone and delay the tick. The catch-up rules above are the honest answer: one late run, labeled late. `time.monotonic()` on Linux does not advance during suspend, so it already measures awake time, which is what Hermes's SleepWatch builds by hand. After a reboot, the bridge needs Termux:Boot to start again; `~/.termux/boot/` exists on the phone (it starts sshd) but restarting the bridge from it is not set up or verified.
- **Approvals need a person.** Hermes auto-approves tools in cron. Chelus asks through Telegram buttons, and nobody presses them at 3 a.m. Proposed rule: a cron run may use a risky tool only under an existing "always" grant (`tool_grants`, `skill_grants`); anything else is denied with a result saying the run is unattended, and the delivered report lists what was denied. The owner then grants it once from chat. No new approval system is needed.
- **SQLite is already there.** Hermes keeps jobs in JSON with file locks and claim fields, and the ledger in SQLite. Chelus can put both in `store.py`. A compare-and-swap update (`UPDATE ... SET next_run_at=? WHERE id=? AND next_run_at=?`) replaces `fire_claim`, `run_claim` and the lock layers, because only the row that changes wins.
- **The cache-stable prompt stays stable.** A cron session is a new session with its own system prompt, so nothing changes there. When a job's output is delivered to the owner, the delivery should also be noted for the owner's next chat turn, riding in that user message like the `[sent ...]` stamp, so "do it" in reply to a reminder has context. This is Hermes's `attach_to_session`, rebuilt the Chelus way.
- **Overlap with chelus-brainstem.** The Upstash job queue on Vercel survives the phone being off, but it can't run the agent. On-phone cron is the scheduler. Brainstem could later serve as an outside heartbeat that notices the phone missed a wake; leave it separate for now.

## Port list, in priority order

Sizes are estimates for Chelus. The whole list is about 1,000 lines against Hermes's 15,000.

All nine items are built (`schedule.py`, `cron.py`, the cron tables in `store.py`, the tick in `telegram.py`, `chelus cron` in the terminal) and pass on the phone, DST cases included; one live job ran on time on 2026-10-28, with its shell call denied and the result delivered. Delivery (item 5) and failure handling (item 7) were finished on 2026-10-31; a live run that day was delivered with a confirmed message id, the stop footer and the next-turn note. The unreachable-model retries are covered by tests only. Script jobs (item 8) and `/cron` (item 9) were added the same day; a live no-model battery script job was delivered, and `/cron` is covered by tests. Choices made while building:

- A one-shot fires up to 30 minutes late (labeled late), not Hermes's 120 s: Doze delays the tick, and a reminder a few minutes late is still worth sending. Later than that it is not run, and the owner is told.
- A run may take 15 awake minutes, checked at each tool call and model reply.
- The cron tool (`cron_tool.py`) asks the owner before create, update, resume, run and remove, with once or deny only, and scans the prompt before asking. The prompt scan (`cron_scan.py`) also runs in `cron.create`, `cron.update` and before every run, so the terminal and a hand-edited database are covered too. `run` marks the job due and returns; Hermes's background run with a result handle needs a gateway Chelus doesn't have.
- Run sessions are marked `origin = 'cron'`, so `chelus chat` never resumes one.
- Delivery counts only with a message id back from Telegram. Every delivered message, failures and missed-run notices too, is kept as a note (the last 5, 800 characters each) and put in front of the owner's next Telegram message to the model, never into the system prompt. The chat history shows only what the owner typed.
- The unreachable-model retry needs a transient provider error with no model reply in the run, a recurring job and a scheduled (not manual) run. It never goes past the job's next regular run. Held attempts don't count toward the failure streak or `repeat`. The streak nudge comes once, on the third failure in a row.
- A failing script is reported straight to the owner without a model call; Hermes hands the error to the model to report. Empty script output skips the model, as in Hermes. Scripts get 5 minutes, not Hermes's hour, and 16 KB of output. Their environment drops every variable whose name contains KEY, TOKEN, SECRET, PASSW, CREDENTIAL or AUTH, a broader net than Hermes's provider-key list. Hermes's per-job interpreter and workdir are not ported: `.sh` and `.bash` run with bash, the rest with Chelus's own Python, from the work folder.
- The model's cron tool can attach an existing script to a job, with the script named on the approval card, but its file tools cannot write one, because they protect the data folder. A script gets there only from the owner or from a shell command the owner approved.
- `/cron` acts without asking, since the owner typed it. Its `run` marks the job due, and the tick right after the command runs it.
- Approvals in a run: only grants saved with "Always" count, never a conversation's "Allow for this conversation". The owner agreed to this rule on 2026-10-28.

Later, once the above runs live: `continuity`/`context_from` (a job sees its own or another job's last output, clipped to 8,000 characters head and tail), the `monitor` gate (skip the model when a URL or script output hasn't changed), the per-job notepad, incidents with acknowledgement, and the quota hold.

Not porting: profiles and satellites, the detached worker and its delivery queue, relay and E2EE adapters, multi-platform and broadcast delivery targets, bot-chat, blueprints and suggestions, kanban, per-job model and provider pins, `workdir`, `enabled_toolsets`, the lifecycle guard (Chelus has no gateway service to restart; revisit if the bridge gets a supervisor) and a send_message tool. Chelus has one chat, and the final answer is the message.
